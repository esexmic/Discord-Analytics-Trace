TRACE BY XYB — REGISTRO DE CAMBIOS DE APARIENCIA
================================================

Este archivo lleva el control de todo lo que se ve en el panel: marca, logo,
colores, tipografía, pantallas, avatares y animaciones. La idea es que en el
futuro estos valores se puedan editar desde una página web sin descargar nada;
acá queda anotado dónde vive cada uno para exponerlos después.

Ruta base: public/index.html (markup), public/app.css (design system) y
public/app.js (estado, fetch, SSE y render). Desde v1.4 el panel ya no tiene
CSS ni JS inline.
Imagen de marca: public/logo.jpg (original en logo/logo.jpg).

v1.4 — 26/10/2026
------------------------------------------------------------

ARCHIVOS
- El panel se parte en tres: public/index.html (markup), public/app.css y
  public/app.js. Nada de CSS/JS inline ni de fetch armados en el HTML.
- Sin fuentes ni assets externos: system-ui, logo local, cero peticiones de red
  salvo la API propia.

DISEÑO
- Design system en :root: --bg, --bg-2, --panel, --panel-2, --line, --line-2,
  --text, --muted, --muted-2, --accent, --accent-2, --accent-soft, --green,
  --red, --amber, --cyan, --purple, --r/--r-sm/--r-xs, --mono, --ease, --shadow.
- Layout de tres zonas: sidebar (cuenta + objetivos), main (stats, toolbar,
  chips, feed) y dialogs (ajustes, buscador de servers).
- Breakpoints 1020 / 860 / 480: la sidebar pasa a drawer con scrim y aparece
  una tabbar fija abajo con el contador y el estado en vivo.
- Tarjetas de evento con icono por tipo, avatar con fallback al default de
  Discord por id, diffs para edit (antes rayado, después destacado) y pills
  para presencia/dispositivo.
- Skeletons en el feed y en la barra lateral mientras carga el bootstrap;
  dialogs con @starting-style para la entrada; todo respeta
  prefers-reduced-motion.

QUÉ SE LLEVÓ PUESTO
- Pantalla de configuración de Supabase, campo de URL/keys y botón "Probar
  conexión": la infraestructura ahora es solo del deploy (variables de entorno).
- Key de acceso en el registro, campo "repetir key", fila "Ver key" en Ajustes
  y toda la sección API keys (crear, copiar, revocar).
- Registro abierto: se entra con usuario + contraseña y nada más. La primera
  cuenta queda como admin.

FLUJO NUEVO
- Boot: login/registro → tarjeta de "pegá tu token de Discord" → fijar
  objetivo → feed. Tres pasos, todos en la misma pantalla.
- Objetivos optimistas: se dibujan al click y revierten solo si la API rechaza.
- Feed y búsqueda de miembros con AbortController + secuencia, así una
  respuesta vieja no pisa una nueva.
- Contadores de la barra lateral actualizados en local desde el SSE, sin
  request extra por evento.

PENDIENTE PARA LA PÁGINA WEB FUTURA

v1.6 — 26/10/2026 · HISTORIAL POR CUENTA (borrado selectivo)
===========================================================

DÓNDE VIVE
- Dialog #history en index.html, con .modal--wide (el mismo ancho que #admin).
- Lógica en public/app.js, sección "historial" (justo después de la de admin).
- Estilos en public/app.css, bloque .hfilters / .hsum / .hlist / .hrow / .hbar.
- Server: GET y DELETE /api/admin/accounts/:user/history en src/server.js.

CÓMO SE VE
- Cada .acct del panel de gestión suma un botón "Historial" (siempre primero en
  .acct__actions). No aparece cuando no hay base de datos configurada.
- .hfilters: select de tipo (mensajes / voz / presencia / perfil), select de
  rango (24 h / 7 d / 30 d / siempre), input de texto y botón Filtrar.
- .hsum: línea en mono con el total ("16 eventos en el historial", "4 eventos
  con el filtro · 2 seleccionados").
- .hlist: scroll de hasta 46vh. Cada .hrow es checkbox + .hrow__icon (mismo
  icono y color por tipo que el feed) + usuario, verbo, fecha y hora, texto del
  evento y las tags de canal/servidor.
- .hbar abajo: "Seleccionar lo cargado" a la izquierda; a la derecha
  "Borrar selección (N)", "Borrar los N del filtro" (solo con filtro activo) y
  "Borrar todo".

ESTADO Y FLUJO
- state.history = { user, rows, total, hasMore, checked:Set, seq, controller,
  busy }. null cuando se cierra el dialog.
- loadHistory() corta la request anterior con AbortController + seq, como el
  feed: cambiar de filtro o de cuenta nunca deja una respuesta vieja pisando la
  nueva.
- historyMeta() es la parte que toca la barra; los checkboxes llaman solo a
  historyMeta(), no re-renderizan la lista, así la selección no pierde el
  scroll.
- Borrar selección manda los ids en lotes de 500 (HISTORY_CHUNK); "Borrar todo"
  y "Borrar los N del filtro" piden un segundo clic y se revierten solos a los
  4s, igual que el botón Borrar de una cuenta.
- Después de borrar: se recargan el historial y la grilla de cuentas, se
  invalida el resumen de esa cuenta y, si el historial era el propio, también se
  recarga el feed.

NO CAMBIA
- Sigue sin hacer falta correr schema.sql: se usa events.id (bigserial) y los
  índices por owner que ya trajo la v3.
- El borrado siempre va filtrado por owner del lado del server; un id de otra
  cuenta en la selección no borra nada afuera.

- Remitente "Xyb Trace" con avatar /logo.jpg (el logo que ya es favicon).
- Un embed por evento, hasta 10 por mensaje: título = ícono + acción + nombre

ESTADO Y FALLOS

- Quitar el webhook, borrar o bloquear la cuenta llaman webhooks.forget(owner):
  se borra la cache de la URL y lo que estaba en espera.
- PUBLIC_URL fija el origen del avatar; si no está, se aprende de una request
  autenticada. localhost = embed sin foto, el resto anda igual.
